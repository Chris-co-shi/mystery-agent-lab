# Mystery Agent Lab V0.2.0 剧本生成规则 v1.0

## 1. 文档定位

本文档用于规范 Mystery Agent Lab 在 V0.2.0 阶段的剧本生成方式。

它的目标不是生成一篇好看的故事大纲，而是生成一份可以被当前项目代码加载、调查、询问、复盘、提交和评分的可运行剧本。

用户可以用自然语言描述剧本需求，例如：

```text
我要一个赛博朋克风格、密室杀人、复杂人物关系的剧本。
```

或：

```text
我要一个民国风、家族遗产争夺、6 个 NPC、中等难度、60 分钟内能玩完的剧本。
```

生成器应根据需求输出结构合法、线索闭环、调查可推进、NPC 不泄底、最终可确定性评分的 GameScript。

---

## 2. V0.2.0 剧本生成总目标

V0.2.0 的剧本生成目标只有一句话：

> 生成一份玩家能通过调查对象发现线索，并基于轻量案件笔记完成一次可解释评分推理的剧本。

本阶段不追求完整内容平台能力，不追求复杂知识图谱，不追求 Agent Runtime，也不追求大型多人剧本。

---

## 3. 文档拆分原则

剧本生成规范必须区分四类内容：

1. 剧本创作规则：如何设计题材、人物、关系、线索、密室、红鲱鱼。
2. V0.2.0 GameScript 运行协议：当前代码真正需要加载的字段。
3. 生成后校验规则：生成结果是否结构合法、线索闭环、可评分。
4. Prompt 模板：如何让 LLM 或 Codex 根据用户需求生成剧本。

不要把创作辅助字段、运行协议字段和未来版本设想混在一起。

---

# 第一部分：剧本创作规则

## 4. 用户需求输入

用户可以用自然语言描述剧本需求。

### 4.1 最小需求

```text
我要一个密室杀人剧本。
```

### 4.2 推荐需求

```text
我要一个赛博朋克风格、6 个 NPC、密室杀人、复杂关系、中等偏高难度、60 分钟内能玩完的剧本。
```

### 4.3 可识别参数

生成器应尽量识别以下参数：

- 题材风格：现代、古风、民国、赛博朋克、科幻、校园、职场、医院、孤岛、游轮、太空站等。
- 案件类型：密室、毒杀、坠楼、失踪、伪装自杀、意外伪装、连环案件等。
- NPC 数量：默认 4-6 个。
- 关系复杂度：简单、中等、复杂。
- 推理难度：简单、中等、困难。
- 游玩时长：30 分钟、60 分钟、90 分钟。
- 是否密室：默认否，用户要求时开启。
- 是否红鲱鱼：默认允许 1-2 个。
- 是否多凶手：默认单凶手，除非用户明确要求。

---

## 5. V0.2.0 默认剧本规模

为了避免当前阶段过早膨胀，V0.2.0 默认生成规模应控制在：

| 项目 | 推荐范围 |
|---|---:|
| NPC 数量 | 4-6 个 |
| 线索数量 | 10-16 条 |
| 调查对象 | 6-10 个 |
| 关键证据 | 4-6 条 |
| 红鲱鱼 | 1-2 个 |
| 游玩时长 | 30-60 分钟 |

10 人以上、20 条以上线索、复杂多层关系网络的剧本可以作为压力测试样例，但不作为 V0.2.0 默认生成目标。

原因：

- CLI 展示会过长。
- NPC 问答上下文容易膨胀。
- Case Notebook 会变得难读。
- 当前 RuleJudge 和 Notebook 仍是 MVP。
- NPC 越多，知识边界越容易混乱。

---

## 6. 公平推理原则

生成的剧本必须保证真相可以从玩家可获得的信息中推出。

禁止：

- 关键事实只存在于 truth 字段中，不存在于线索或证言中。
- 凶手身份完全依赖作者解释。
- 关键证据无法被玩家发现。
- 作案手法没有物证、现场痕迹或证言支撑。
- 作案动机没有人物关系、利益冲突、证言或背景支撑。
- HIDDEN 线索成为主线推理必需线索。

要求：

- 凶手判断至少有 2 条支撑线索或证言。
- 作案动机至少有 1 条支撑线索、关系或证言。
- 作案手法至少有 2 条支撑线索。
- 关键证据必须可通过 PUBLIC 线索或 investigation_targets 发现。
- 红鲱鱼必须能被后续线索反证。

---

## 7. 人物设计规则

### 7.1 characters 只放公开信息

characters 用于玩家可见的人物信息，不放私密真相、不放完整谎言规则。

推荐字段：

```json
{
  "id": "npc_doctor",
  "name": "周医生",
  "role": "私人医生",
  "is_npc": true,
  "is_victim": false,
  "public_profile": "死者长期私人医生，案发当晚也在现场。",
  "relationship_to_victim": "私人医生"
}
```

### 7.2 npc_profiles 放私有信息和问答边界

npc_profiles 用于 NPC 私有背景、已知事实、秘密、谎言规则、禁止知识等。

推荐字段：

```json
{
  "character_id": "npc_doctor",
  "private_background": "曾被死者长期勒索。",
  "known_facts": [],
  "secrets": [],
  "lie_rules": [],
  "forbidden_knowledge": [],
  "personality": "冷静、克制、回避细节",
  "alibi_claim": "晚宴后去书房送过药。",
  "possible_motive": "被死者勒索"
}
```

### 7.3 死者处理规则

死者必须被明确标识。

推荐方式：

```json
{
  "id": "victim_gu",
  "name": "顾明远",
  "role": "死者",
  "is_npc": false,
  "is_victim": true,
  "public_profile": "企业董事长，案发当晚死于书房。"
}
```

不要让 murderer_id 指向死者。

---

## 8. 人物关系规则

relationships 对复杂剧本生成很有价值，但在 V0.2.0 中不作为运行时必填字段。

定位：

- 可以作为生成期辅助信息。
- 可以作为可选展示信息。
- 当前运行时不强依赖。
- 没有 relationships 时，剧本仍然必须能加载和游玩。

可选结构：

```json
{
  "source_character_id": "npc_doctor",
  "target_character_id": "victim_gu",
  "relation_type": "勒索关系",
  "description": "死者掌握周医生违规用药的证据，并长期勒索他。",
  "is_public": false,
  "related_clue_ids": ["clue_blackmail_record"]
}
```

复杂关系剧本建议包含：

- 主要矛盾线。
- 隐藏关系线。
- 误导动机线。
- 真凶核心动机线。
- 证言冲突线。

但这些不应成为 V0.2.0 的硬运行依赖。

---

## 9. 线索设计规则

### 9.1 V0.2.0 必填字段

```json
{
  "id": "clue_wine_glass",
  "title": "红酒杯残留异味",
  "content": "死者手边摔碎的红酒杯中有一股异常苦味。",
  "visibility": "LOCKED"
}
```

必填字段：

- id
- title
- content
- visibility

### 9.2 V0.2.0 可选字段

以下字段可用于增强 Case Notebook，但不能作为运行时硬依赖：

- importance
- related_character_ids
- related_target_ids
- clue_type
- reasoning_tags
- search_keywords
- is_key_clue

示例：

```json
{
  "id": "clue_wine_glass",
  "title": "红酒杯残留异味",
  "content": "死者手边摔碎的红酒杯中有一股异常苦味。",
  "visibility": "LOCKED",
  "clue_type": "PHYSICAL_EVIDENCE",
  "related_character_ids": ["npc_doctor"],
  "related_target_ids": ["target_body", "target_wine_glass"],
  "reasoning_tags": ["METHOD", "POISON", "EVIDENCE"],
  "is_key_clue": true
}
```

### 9.3 visibility 规则

支持：

- PUBLIC：开局可见。
- LOCKED：通过 investigation_targets 调查发现。
- HIDDEN：V0.2.0 保留字段，不作为主线推理必需线索。

要求：

- PUBLIC 线索不能直接泄露真凶或完整手法。
- LOCKED 线索应绑定到 investigation_targets。
- HIDDEN 线索不能影响 V0.2.0 主线推理闭环。

---

## 10. 红鲱鱼规则

红鲱鱼可以误导玩家，但必须可被反证。

合格红鲱鱼：

- 看似指向某个嫌疑人。
- 与真实动机或手法有一定相似性。
- 后续有线索能够解释或推翻。
- 不会成为无法排除的假真相。

禁止：

- 随机放置无意义误导线索。
- 让红鲱鱼比真相证据更强，但没有反证。
- 通过作者解释强行排除红鲱鱼。

---

## 11. 密室剧本规则

如果用户要求密室，必须显式设计密室机制。

密室机制至少包含：

- 表面密室状态。
- 实际进入或离开方式。
- 伪装手段。
- 误导玩家的现象。
- 破解密室的关键线索。

建议在 truth 中增加可选结构：

```json
{
  "locked_room_mechanism": {
    "apparent_state": "房门从内部反锁，窗户关闭，监控显示无人进入。",
    "actual_method": "凶手提前设置延时门锁，制造内部反锁假象。",
    "misdirection": "监控时间被篡改，玩家误以为案发时无人靠近。",
    "supporting_clue_ids": [
      "clue_door_lock_scratch",
      "clue_access_log_gap"
    ]
  }
}
```

此字段 V0.2.0 可选，但如果用户明确要求密室，推荐生成。

---

## 12. NPC 不泄底规则

NPC 可以：

- 表达主观怀疑。
- 因偏见误导玩家。
- 为保护自己隐瞒部分事实。
- 说谎掩盖自己的动机。
- 根据自己已知事实提出不完整判断。

NPC 不可以：

- 上帝视角直接说出真凶。
- 直接说出完整作案手法。
- 编造剧本中不存在的线索。
- 知道自己不该知道的信息。
- 把主观怀疑说成确定事实。

允许示例：

```text
我觉得周医生很可疑，他那晚确实去过书房。
```

禁止示例：

```text
我知道周医生就是凶手，他把镇静剂放进红酒里杀了人。
```

# 第二部分：V0.2.0 GameScript 运行协议

## 13. 顶层字段

V0.2.0 推荐使用扁平 GameScript 协议，不新增 metadata/public_intro 作为必填顶层对象。

推荐顶层结构：

```json
{
  "id": "cyber_locked_room_001",
  "title": "霓虹塔密室",
  "version": "v0.2.0",
  "genre": "赛博朋克",
  "difficulty": "MEDIUM",
  "estimated_minutes": 60,
  "background": "玩家开局可见的案情简介。",
  "rules": {},
  "characters": [],
  "npc_profiles": [],
  "clues": [],
  "investigation_targets": [],
  "truth": {},
  "timeline": []
}
```

### 13.1 必填顶层字段

- id
- title
- version
- background
- rules
- characters
- npc_profiles
- clues
- truth

### 13.2 V0.2.0 新增或强化字段

- genre：可选。
- difficulty：可选。
- estimated_minutes：可选。
- investigation_targets：V0.2.0 核心字段，推荐必填。
- timeline：可选。
- relationships：可选，生成期辅助，不作为运行时硬依赖。

---

## 14. rules.scoring 协议

rules 中必须支持 scoring。

默认配置：

```json
{
  "rules": {
    "scoring": {
      "murderer_score": 40,
      "key_evidence_score": 30,
      "motive_score": 15,
      "method_score": 15
    }
  }
}
```

要求：

- 总分建议为 100。
- 每个部分分数必须大于 0。
- 旧剧本缺失 scoring 时，程序可使用默认配置。
- 新生成剧本必须显式生成 scoring。

---

## 15. truth 协议

truth 是最终判案标准答案。

必须包含：

```json
{
  "murderer_id": "npc_doctor",
  "motive": "被死者长期勒索，担心违规用药记录曝光。",
  "method": "将镇静剂混入红酒，使死者失去意识后制造密室假象。",
  "key_evidence_ids": [
    "clue_wine_glass",
    "clue_lip_color",
    "clue_blackmail_record"
  ],
  "motive_keywords": ["勒索", "曝光", "违规用药"],
  "method_keywords": ["镇静剂", "红酒", "投药"]
}
```

### 15.1 motive_keywords / method_keywords

V0.2.0 使用简单字符串数组。

要求：

- 关键词数量建议 2-5 个。
- 关键词应包含玩家可能输入的常见表达。
- 不要使用过长句子作为关键词。
- 不要使用过度文学化表达。

### 15.2 keyword_groups 未来预留

后续可升级为：

```json
{
  "method_keyword_groups": [
    ["镇静剂", "安眠药", "药物", "下药"],
    ["红酒", "酒", "饮品", "杯子"],
    ["投药", "混入", "加入"]
  ]
}
```

V0.2.0 暂不实现 keyword_groups。

---

## 16. investigation_targets 协议

investigation_targets 是 V0.2.0 的核心新增字段。

### 16.1 支持类型

- ROOM
- BODY
- ITEM

### 16.2 字段结构

```json
{
  "id": "target_body",
  "name": "顾明远的尸体",
  "type": "BODY",
  "description": "顾明远倒在书房地毯上，嘴唇发紫，手边有一只摔碎的红酒杯。",
  "search_keywords": ["尸体", "死者", "嘴唇", "酒杯"],
  "discoverable_clue_ids": [
    "clue_wine_glass",
    "clue_lip_color"
  ]
}
```

### 16.3 生成要求

每个 V0.2.0 剧本建议包含：

- 1 个 BODY 类型目标。
- 1-3 个 ROOM 类型目标。
- 2-6 个 ITEM 类型目标。

### 16.4 线索分布规则

- 普通调查对象建议解锁 1-3 条线索。
- 核心调查对象最多解锁 4 条线索。
- 关键证据应分散在 BODY / ROOM / ITEM 多类对象中。
- 不要让一个 investigation_target 解锁所有关键证据。
- 不要让关键证据只依赖 /search。

---

## 17. /case 降级展示规则

Case Notebook 在 V0.2.0 是轻量读模型。

它只需要展示：

- 已发现线索。
- NPC 问答。
- 调查过的对象。
- 可提交证据候选。

它不做：

- 自动推理。
- 嫌疑人归因。
- 完整时间线整理。
- 知识图谱。
- LLM 总结。

当 clue metadata 缺失时，必须降级展示：

- 没有 clue_type：展示为未分类线索。
- 没有 related_target_ids：只展示标题和内容。
- 没有 reasoning_tags：不展示推理方向。
- 没有 relationships：不展示关系网络。

# 第三部分：生成后校验规则

## 18. 结构校验

生成后的剧本必须满足：

- id 非空。
- title 非空。
- background 非空。
- characters 非空。
- clues 非空。
- truth 非空。
- rules.scoring 存在。
- investigation_targets 存在。

---

## 19. ID 引用校验

必须检查：

- truth.murderer_id 存在于 characters。
- truth.murderer_id 不指向死者。
- truth.key_evidence_ids 全部存在于 clues。
- investigation_targets.discoverable_clue_ids 全部存在于 clues。
- npc_profiles.character_id 全部存在于 characters。
- clue.related_character_ids 如存在，必须引用 characters 中已有 ID。
- clue.related_target_ids 如存在，必须引用 investigation_targets 中已有 ID。
- locked_room_mechanism.supporting_clue_ids 如存在，必须引用 clues 中已有 ID。

---

## 20. 推理闭环校验

必须检查：

- 凶手判断有线索或证言支撑。
- 动机有线索、关系或证言支撑。
- 手法有物证、现场痕迹或证言支撑。
- 关键证据可被玩家发现。
- truth.key_evidence_ids 不能全部是 HIDDEN。
- HIDDEN 线索不能成为 V0.2.0 主线推理必需条件。
- 红鲱鱼有反证线索。

---

## 21. 评分校验

必须检查：

- rules.scoring 存在。
- murderer_score > 0。
- key_evidence_score > 0。
- motive_score > 0。
- method_score > 0。
- 总分建议为 100。
- truth.motive_keywords 存在且非空。
- truth.method_keywords 存在且非空。

---

## 22. NPC 不泄底校验

必须检查：

- PUBLIC 信息没有直接写出真凶。
- PUBLIC 信息没有直接写出完整作案手法。
- NPC 可见信息不包含上帝视角真相。
- NPC 的主观怀疑必须使用不确定语气。
- NPC 不得编造 clues 中不存在的关键线索。
- forbidden_knowledge 不应与 NPC 已知事实冲突。

---

## 23. 生成失败条件

出现以下任一情况，必须重新生成或拒绝输出：

1. 凶手不唯一。
2. murderer_id 不存在。
3. murderer_id 指向死者。
4. 关键证据无法被玩家发现。
5. 真相依赖 HIDDEN 线索。
6. method 没有任何物证、现场痕迹或证言支撑。
7. motive 没有任何人物关系、证言或线索支撑。
8. investigation_targets 中 discoverable_clue_ids 引用不存在。
9. rules.scoring 缺失。
10. truth.motive_keywords 缺失。
11. truth.method_keywords 缺失。
12. PUBLIC 线索直接写出凶手或完整作案手法。
13. NPC 直接泄露真凶或完整手法。
14. 红鲱鱼无法被反证。
15. 剧本需要代码不支持的地图、道具组合或复杂触发系统才能玩。

---

# 第四部分：剧本生成 Prompt 模板

## 24. 标准 Prompt 模板

```text
请为 Mystery Agent Lab 生成一个符合 V0.2.0 剧本协议的可运行剧本。

用户需求：
{user_requirement}

生成目标：
1. 剧本必须可用于单人 CLI 推理游戏。
2. 玩家应能通过 investigation_targets 调查地点、尸体、物品发现线索。
3. /search 只作为已知信息检索，不作为主要线索解锁方式。
4. 剧本必须包含 characters、npc_profiles、clues、investigation_targets、truth、rules.scoring。
5. truth 必须包含 murderer_id、motive、method、key_evidence_ids、motive_keywords、method_keywords。
6. LOCKED 线索必须能通过 investigation_targets 发现。
7. HIDDEN 线索不能作为 V0.2.0 主线推理必需线索。
8. NPC 可以主观怀疑、隐瞒、撒谎，但不能直接泄露真凶和完整手法。
9. 必须有唯一可解释真相。
10. 必须有可评分结构。
11. 默认剧本规模控制在 4-6 个 NPC、10-16 条线索、6-10 个调查对象。
12. 如果用户要求 10 人以上复杂剧本，请标记为压力测试剧本，并提醒其不属于 V0.2.0 默认规模。

输出要求：
1. 剧本设计摘要。
2. 人物关系摘要。
3. 关键证据链摘要。
4. 完整 GameScript JSON。
5. 自检结果。

请在输出前自检：
- ID 引用是否一致。
- 凶手是否唯一。
- 关键证据是否可发现。
- scoring 是否存在。
- motive_keywords/method_keywords 是否存在。
- investigation_targets 是否覆盖关键 LOCKED 线索。
- HIDDEN 线索是否不影响主线推理。
- NPC 是否没有直接泄底。
- 最终真相是否可以由线索推出。
```

---

## 25. 输出格式要求

生成器应输出：

```text
一、剧本设计摘要
二、人物关系摘要
三、关键证据链摘要
四、完整 GameScript JSON
五、自检结果
```

其中完整 GameScript JSON 必须是可复制、可校验、可加载的 JSON 数据。
