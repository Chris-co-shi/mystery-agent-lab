# Mystery Agent Lab V0.2.0 调查机制 MVP 迭代计划（收敛版）

版本：V0.2.0 Investigation MVP  
状态：工作基线计划  
适用项目：Mystery Agent Lab / AI 剧本杀  
更新时间：2026-06-03

---

## 1. 版本目标

V0.2.0 只验证一件核心事情：

> 玩家能通过调查对象发现线索，并基于轻量案件笔记完成一次可解释评分的推理。

本版本不是 Tool 化版本，不是 Agent Runtime 版本，也不是完整剧本杀平台版本。它的目标是把当前 CLI 从“开发者可玩的线索搜索 Demo”推进到“普通玩家能理解的调查推理 MVP”。

完成后，玩家应能走通以下主链路：

```text
开始游戏
查看公开案情
调查地点、尸体、物品
发现线索
询问 NPC
检索已知信息
查看案件笔记
提交最终推理
查看评分拆解
导出本局记录
```

---

## 2. 当前代码基础判断

V0.1.3 已经具备以下基础能力，可以作为 V0.2.0 的演进基础：

- `case_records`：已经可以记录玩家行为，是后续 `/review`、`/case`、导出的数据来源。
- `/review`：已经具备复盘雏形，可以继续演进为行为时间线复盘。
- `SessionRecorder`：已经支持会话导出，可以继续增强 JSON / Markdown 输出。
- `RuleJudge`：已有确定性判案入口，但当前评分逻辑过于硬编码。
- `ClueSearchService`：已有线索搜索与解锁能力，但 V0.2.0 不应直接改变其历史语义。

因此，V0.2.0 的合理方向是：

- 在现有记录和复盘能力上增加调查机制。
- 在现有 RuleJudge 上增加评分配置化和 score_breakdown。
- 新增已知信息检索服务，而不是直接破坏旧 ClueSearchService。
- 用轻量案件笔记补齐最终提交前的上下文缺口。

## 4. 关键收敛原则

### 4.1 不先做完整 CLI 去 ID 化

原计划中 `TASK-000` 放在第一位，覆盖 `/ask`、`/investigate`、`/submit`、`/search`、`/review`、`/case`。这个范围过大，容易把 UI、服务、状态模型和测试一起搅在一起。

调整后：

- 先完成评分、调查对象模型、调查服务和 `/investigate` 主链路。
- 在 `/submit` 阶段优先完成关键路径去 ID 化。
- 最后抽出通用选择器，统一收敛 CLI 去 ID 化。

### 4.2 线索元数据只做可选字段

`clue_type`、`related_target_ids`、`reasoning_tags` 对 Notebook 展示有帮助，但不能成为 V0.2.0 的硬门槛。

规则：

- 字段可选。
- 有字段就增强展示。
- 没字段就降级展示线索标题和内容。
- Validator 只校验明显错误，不强制每条线索都填写完整元数据。

### 4.3 不直接改变 ClueSearchService 语义

当前 `ClueSearchService` 的历史语义是“搜索并解锁线索”。如果直接改成“只搜索已知信息”，会破坏旧测试和内部行为。

调整后：

- 保留 `ClueSearchService`。
- 新增 `KnownInfoSearchService`。
- CLI `/search` 在 V0.2.0 使用 `KnownInfoSearchService`。
- 旧 `ClueSearchService` 作为兼容能力保留，后续再逐步迁移。

### 4.4 Case Notebook 只做轻量 MVP

V0.2.0 的 `/case` 不做自动推理，不做嫌疑人归因，不做完整时间线。

MVP 只展示：

- 已发现线索。
- NPC 问答。
- 调查过的对象。
- 可提交证据候选。

时间线、嫌疑人关联、物证分类可以基于已有可选字段增强展示，但不能成为必需能力。

### 4.5 动机和手法评分必须补充关键词 schema

当前 truth 中通常只有 `motive` 和 `method` 文本。若要稳定判断“勒死”不命中“镇静剂混入红酒投药”，必须新增显式关键词字段。

建议新增：

```text
truth.motive_keywords
truth.method_keywords
```

或使用等价 scoring 字段。推荐放在 `truth` 下，因为它属于真相判定依据，不只是评分权重。

## 5. 核心数据模型规划

### 5.1 ScoringConfig

剧本 rules 中新增评分配置：

```json
{
  "rules": {
    "scoring": {
      "murderer_score": 40,
      "key_evidence_score": 30,
      "motive_score": 15,
      "method_score": 15
    }
  }
}
```

旧剧本没有 scoring 时，使用默认配置：

```text
murderer_score = 40
key_evidence_score = 30
motive_score = 15
method_score = 15
```

### 5.2 Truth 关键词字段

建议在 truth 中新增：

```json
{
  "truth": {
    "murderer_id": "npc_doctor",
    "motive": "长期被死者勒索，因此决定杀人灭口。",
    "method": "将镇静剂混入红酒，导致死者中毒后昏迷死亡。",
    "motive_keywords": ["勒索", "灭口"],
    "method_keywords": ["镇静剂", "红酒", "投药", "中毒"]
  }
}
```

评分时：

- 凶手：按 `murderer_id` 命中。
- 关键证据：按 clue id 命中。
- 动机：按 `motive_keywords` 命中。
- 手法：按 `method_keywords` 命中。

### 5.3 ScoreBreakdown

`FinalVoteEvaluation` 增加：

```text
score_breakdown:
  murderer:
    score
    max_score
    matched
    reason

  key_evidence:
    score
    max_score
    matched_clue_ids
    missing_clue_ids
    reason

  motive:
    score
    max_score
    matched_keywords
    missing_keywords
    reason

  method:
    score
    max_score
    matched_keywords
    missing_keywords
    reason
```

### 5.4 InvestigationTarget

新增最小调查对象模型：

```text
InvestigationTarget:
  id
  name
  type
  description
  search_keywords
  discoverable_clue_ids
```

`type` 支持：

```text
ROOM
BODY
ITEM
```

示例：

```json
{
  "id": "target_body",
  "name": "顾明远的尸体",
  "type": "BODY",
  "description": "顾明远倒在书房地毯上，嘴唇发紫，手边有一只摔碎的红酒杯。",
  "search_keywords": ["尸体", "死者", "嘴唇", "酒杯"],
  "discoverable_clue_ids": ["clue_wine_glass", "clue_lip_color"]
}
```

### 5.5 可选线索元数据

可选字段：

```text
clue_type
related_character_ids
related_target_ids
related_time_label
reasoning_tags
```

示例：

```json
{
  "id": "clue_wine_glass",
  "title": "红酒杯残留异味",
  "content": "死者手边摔碎的红酒杯中有一股异常苦味。",
  "visibility": "LOCKED",
  "clue_type": "PHYSICAL_EVIDENCE",
  "related_character_ids": ["npc_doctor"],
  "related_target_ids": ["target_body", "target_wine_glass"],
  "related_time_label": "晚宴后",
  "reasoning_tags": ["METHOD", "POISON", "EVIDENCE"]
}
```

降级规则：

- 没有 `clue_type`：展示为普通线索。
- 没有 `related_target_ids`：不展示关联对象。
- 没有 `reasoning_tags`：不展示推理标签。
- 不因为缺少这些字段导致剧本加载失败。

## 6. 服务设计

### 6.1 InvestigationService

职责：根据当前 `GameState` 和调查对象 ID 执行调查。

输入：

```text
GameState
target_id
```

输出：

```text
InvestigationResult
```

建议结构：

```text
InvestigationResult:
  target_id
  target_name
  target_type
  target_description
  newly_discovered_clues
  already_discovered_clues
  ignored_hidden_clues
  message
```

业务规则：

- 调查对象不存在时，返回明确错误，不改变状态。
- 玩家可以重复调查同一对象。
- 重复调查不会重复解锁同一线索。
- 没有新线索时，也要返回清晰提示。
- 普通调查不能解锁 HIDDEN 线索。
- 即使 HIDDEN 线索被误配置到 `discoverable_clue_ids` 中，也必须过滤。

### 6.2 KnownInfoSearchService

职责：搜索玩家当前已知信息。

搜索范围：

- 初始公开线索。
- 已发现线索。
- NPC 问答记录。
- 调查记录。
- case_records 中可展示的行为记录。

明确不做：

- 不解锁新的 LOCKED 线索。
- 不搜索未发现的隐藏线索。
- 不改变 `GameState.discovered_clue_ids`。

### 6.3 CaseNotebookService

职责：从当前状态构建轻量案件笔记。

输入数据来源：

- GameScript。
- GameState。
- discovered clues。
- NPC 问答记录。
- investigation records。
- case_records。

输出：

```text
CaseNotebookView:
  discovered_clues
  npc_dialogues
  investigated_targets
  evidence_candidates
```

MVP 不输出：

- 自动嫌疑人分析。
- 自动推理结论。
- 完整时间线。
- 知识图谱关系。

## 7. CLI 体验设计

### 7.1 `/investigate`

玩家输入：

```text
/investigate
```

系统展示：

```text
【可调查对象】

1. 书房
   类型：地点
   简介：顾明远遇害的房间。

2. 顾明远的尸体
   类型：尸体
   简介：死者倒在书房地毯上，手边有摔碎的酒杯。

3. 摔碎的红酒杯
   类型：物品
   简介：酒杯碎片散落在尸体旁。

请选择要调查的对象编号或名称：
```

玩家可以输入编号，也可以输入名称。

### 7.2 `/search`

V0.2.0 中 `/search` 只搜索已知信息。

示例：

```text
/search 红酒
```

返回：

```text
【搜索结果：红酒】

1. 线索：红酒杯残留异味
   来源：调查「顾明远的尸体」

2. NPC 证言：周医生提到顾明远晚宴时喝过红酒。
```

无结果时：

```text
当前已知信息中没有找到相关内容。你可以继续调查地点、尸体或物品。
```

### 7.3 `/case`

MVP 展示结构：

```text
【案件笔记本】

一、已发现线索
1. 红酒杯残留异味
   内容：死者手边摔碎的红酒杯中有一股异常苦味。
   来源：调查「顾明远的尸体」

二、NPC 问答
1. 周医生
   问题：你最后一次见到顾明远是什么时候？
   回答：晚宴后我去书房给他送过药。

三、已调查对象
1. 顾明远的尸体
   新发现：红酒杯残留异味、死者嘴唇发紫

四、可提交证据候选
1. 红酒杯残留异味
2. 死者嘴唇发紫
```

### 7.4 `/submit`

提交前先展示案件笔记摘要：

```text
【提交最终推理前，请先确认案件笔记】

一、已发现线索
1. 红酒杯残留异味
2. 死者嘴唇发紫

二、NPC 问答摘要
1. 周医生：晚宴后去书房送过药

三、已调查对象
1. 顾明远的尸体
2. 书房

是否开始提交最终推理？
1. 开始提交
2. 返回继续调查
```

正式提交时：

```text
【请选择你认为的凶手】
1. 林伯
2. 顾晓棠
3. 周医生

请输入编号或姓名：
```

关键证据只能从已发现线索中选择：

```text
【请选择关键证据】
1. 红酒杯残留异味
2. 死者嘴唇发紫
3. 书房地毯拖拽痕迹

请输入编号，多个用逗号分隔：
```

### 7.5 `/review` 与 `/history`

规则：

- `/review` 展示完整玩家行为时间线。
- `/history` 不再作为主命令出现在 `/help` 中。
- 输入 `/history` 时，提示该命令已合并到 `/review`，并转发执行 `/review`。

## 8. 任务顺序

### TASK-001：评分配置化

目标：让 RuleJudge 从剧本规则读取评分配置，并输出 score_breakdown。

交付物：

- `ScoringConfig`。
- 默认评分配置。
- `truth.motive_keywords` / `truth.method_keywords` 或等价字段。
- `FinalVoteEvaluation.score_breakdown`。
- 评分单测。

完成标准：

- 旧剧本没有 scoring 也能运行。
- 新剧本可以配置四类评分权重。
- 动机和手法参与评分。
- “勒死”不能命中“镇静剂混入红酒投药”。
- 评分结果能解释每一部分得分来源。

### TASK-002：调查对象模型与剧本协议扩展

目标：让 GameScript 支持 `investigation_targets`。

交付物：

- `InvestigationTarget`。
- `InvestigationTargetType`。
- `GameScript.investigation_targets`。
- 剧本 JSON 示例。
- Validator 最小校验。

完成标准：

- 剧本能声明 ROOM / BODY / ITEM 调查对象。
- 调查对象能关联 `discoverable_clue_ids`。
- 无效 clue id 能被 Validator 发现或 warning。
- 旧剧本没有 `investigation_targets` 时不崩。

### TASK-004：InvestigationService

目标：实现确定性调查服务。

交付物：

- `InvestigationService`。
- `InvestigationResult`。
- 调查对象不存在错误。
- 重复调查逻辑。
- HIDDEN 线索过滤逻辑。
- 服务层单测。

完成标准：

- 调查房间能发现配置线索。
- 调查尸体能发现配置线索。
- 调查物品能发现配置线索。
- 重复调查不会重复解锁。
- HIDDEN 线索不会被普通调查解锁。
- 不存在对象不改变状态。

### TASK-005：case_records 接入调查行为

目标：调查行为进入案件记录。

交付物：

- `CaseActionType.INVESTIGATE`。
- Investigation case record payload。
- `/review` 可展示调查记录。
- JSON / Markdown 可导出调查记录。

完成标准：

- 每次调查都有记录。
- 重复调查也有记录。
- 最终复盘能看到玩家调查路径。
- 导出文件包含调查记录。

### TASK-006：CLI /investigate

目标：玩家可以通过 CLI 完成调查。

交付物：

- `/investigate` 命令。
- 调查对象列表展示。
- 编号选择支持。
- 名称选择支持。
- 调查结果展示。
- 错误输入处理。

完成标准：

- 玩家可以不输入 target_id 完成调查。
- 调查后能看到新发现线索。
- 重复调查提示清晰。
- 调查不存在对象提示清晰。

### TASK-009：/search 降级为已知信息检索

目标：保留 `/search`，但不让它继续主导 V0.2.0 玩法。

交付物：

- `KnownInfoSearchService`。
- `/search` 搜索已发现线索。
- `/search` 搜索 NPC 问答记录。
- `/search` 搜索调查记录。
- `/search` 不解锁新线索。
- 回归测试。

完成标准：

- `/search` 不解锁新的 LOCKED 线索。
- `/search` 可以搜索已知信息。
- `/search` 无结果时提示玩家继续调查。
- 旧 `ClueSearchService` 保留兼容。

### TASK-007：/case 案件笔记本 MVP

目标：玩家可以在最终提交前查看轻量案件笔记。

交付物：

- `/case` 命令。
- `CaseNotebookService`。
- `CaseNotebookView`。
- 已发现线索展示。
- NPC 问答聚合展示。
- 调查对象展示。
- 可提交证据候选展示。

完成标准：

- `/case` 能展示已发现线索。
- `/case` 能按 NPC 展示问答记录。
- `/case` 能展示调查过的对象。
- `/case` 能展示可用于最终提交的证据候选。
- 缺少线索元数据时可以降级展示。

### TASK-008：/submit 去 ID 化 + 提交前展示案件笔记

目标：玩家最终提交前可以查看完整上下文，并通过编号或名称提交推理。

交付物：

- 提交前案件笔记摘要。
- 凶手编号 / 名称选择。
- 证据编号多选。
- 动机输入。
- 手法输入。
- 提交后评分拆解展示。

完成标准：

- `/submit` 前展示案件笔记摘要。
- 玩家可以返回继续调查。
- 玩家选择凶手不需要输入 NPC ID。
- 玩家选择证据不需要输入 clue ID。
- 玩家只能选择已发现线索作为关键证据。
- 提交后展示 score_breakdown。

### TASK-010：/review 替代 /history

目标：`/review` 成为统一时间线复盘入口。

交付物：

- `/review` 展示调查记录。
- `/review` 展示 NPC 问答记录。
- `/review` 展示搜索记录。
- `/review` 展示提交记录。
- `/history` 转发到 `/review`。
- `/help` 不展示 `/history`。

完成标准：

- `/review` 能看到完整玩家行为。
- `/history` 不再作为主命令出现。
- 输入 `/history` 时不会报错。
- 玩家能区分 `/review` 和 `/case`。

### TASK-011：导出增强

目标：JSON / Markdown 导出完整支持 V0.2.0 数据。

交付物：

- JSON 导出 investigation records。
- JSON 导出 score_breakdown。
- Markdown 导出调查记录。
- Markdown 导出案件笔记本。
